# CCZ denúncia dividida em "Animais agressivos" e "Animais doentes" por discriminador `tipo`

A denúncia do CCZ passa a ter dois tipos — "Animais agressivos" (existente) e "Animais doentes" (novo) — reaproveitando o mesmo model `DenunciaCaoAgressivo` (tabela `ccz_denuncias`) e o mesmo formulário. Um campo discriminador `tipo` (`VARCHAR(20)`, NOT NULL, default `'AGRESSIVO'`) separa os registros; as actions de listar/criar ganham o parâmetro `tipo` sem CRUD paralelo, o formulário e a lista são parametrizados por prop, e o menu lateral transforma "Denúncias" num sub-dropdown aninhado no mesmo padrão de "Zoonoses → Esporotricose". A migration é uma `ALTER TABLE ADD COLUMN` não destrutiva, aplicada fora do fluxo `migrate dev`.

Watch for: a migration.sql nova é capturada pelo `*.sql` no `.gitignore` e NÃO aparece em `git status` — um `git add` normal vai commitar o schema/código sem o arquivo de migration (confirmado). Os itens aninhados "Animais agressivos/doentes" perdem o destaque ao trocar da aba Lista para Novo, porque o `path` carrega `subTab=LISTA` (confirmado); divergência pequena de UX frente ao item Esporotricose.

**Verdict**: NEEDS_CHANGES

## High-level view

O discriminador foi modelado como uma única coluna no model existente, sem tocar em nenhum outro model nem na PK `zoonoses_denuncia_pkey`. A migration contém exatamente o `ADD COLUMN ... NOT NULL DEFAULT 'AGRESSIVO'` que corresponde ao schema, no mesmo estilo não destrutivo da migration anterior (`add_animal_situacao`). O coder registrou nas notas que a aplicou via `db execute` + `migrate resolve --applied` e confirmou o estado com `migrate status` — ou seja, nada de `migrate dev`/`reset`.

As duas vias de leitura (server action `listarDenuncias(tipo)` e rota `GET /api/ccz/denuncias?tipo=`) filtram no `where` e, sem o parâmetro, retornam tudo — compatível com callers antigos. A escrita (`salvarDenuncia` e `POST`) grava `tipo` com default `AGRESSIVO`. Não há CRUD duplicado; obter/excluir por id não existem como funções separadas e nada no diff os altera.

O formulário `CadastroDenuncia` e a `DenunciasLista` recebem a prop `tipo` e ajustam apenas rótulo/título/placeholder e o filtro de busca — os campos gravados são idênticos. O roteamento do CCZ ganhou duas abas (`DENUNCIA_AGRESSIVO`, `DENUNCIA_DOENTE`), cada uma reusando a barra Lista/Novo genérica já existente.

A principal pendência não é de comportamento em runtime e sim de entrega: o arquivo de migration está sob uma regra de ignore do git. As migrations anteriores só estão versionadas porque foram adicionadas com `-f`; a nova precisa do mesmo tratamento ou será deixada para trás no commit.

### Discriminador numa só coluna, PK e demais models intactos

O model `DenunciaCaoAgressivo` ganha somente `tipo String @default("AGRESSIVO") @map("tipo") @db.VarChar(20)`. A PK continua `@id(map: "zoonoses_denuncia_pkey")`, o `@@map("ccz_denuncias")` está preservado e nenhum outro model aparece no diff do schema (confirmed). A migration é uma única linha:

```sql
ALTER TABLE "ccz_denuncias" ADD COLUMN "tipo" VARCHAR(20) NOT NULL DEFAULT 'AGRESSIVO';
```

Bate exatamente com o schema (NOT NULL + default) e segue o mesmo formato não destrutivo da migration `20261106140000_add_animal_situacao` já no repo. Por ter default, as 4 denúncias existentes recebem `AGRESSIVO` sem backfill manual (confirmed).

### Migration sob regra de ignore do git

`git check-ignore` confirma que `.gitignore:64:*.sql` captura a nova `migration.sql`; ela entra em "untracked" apenas implicitamente e não é listada por `git status`. As migrations anteriores (`git ls-files prisma/migrations/*.sql`) estão versionadas, o que só é possível porque foram adicionadas com `git add -f` em algum momento. As notas do coder já registram esse lembrete, mas vale tratar como item de entrega: sem o `-f`, o commit leva o schema e o código novos sem o arquivo de migration, deixando ambientes que rodam `migrate deploy` sem a coluna (confirmed).

### Leitura e escrita parametrizadas por `tipo`, sem CRUD paralelo

`listarDenuncias(tipo)` e o `GET` da rota aplicam `where: tipo ? { tipo } : undefined`; chamadas sem o argumento continuam retornando todas as denúncias (confirmed). `salvarDenuncia` e o `POST` gravam `tipo: dados.tipo || "AGRESSIVO"`. Não há funções `obterDenuncia`/`excluirDenuncia` no `actions.js` e nada no diff mexe em busca por id ou exclusão — o requisito de "obter/excluir por id intactos" se sustenta porque essas rotas simplesmente não foram tocadas (confirmed).

Observação de escopo: o `POST` monta `data: { id: novoId, ...dados, tipo: ... }`, espalhando o payload do cliente direto no `create`. Esse spread já existia antes desta mudança (só a linha `tipo` foi adicionada), então está fora do escopo da revisão; fica a nota de que é um padrão de atribuição em massa pré-existente.

### Formulário e lista reusados, segregação por `tipo`

`CadastroDenuncia({ tipo = "AGRESSIVO" })` escolhe rótulo/placeholder/texto do botão por `ROTULOS_POR_TIPO` e envia `{ ...form, tipo }`; os campos gravados são os mesmos nos dois tipos (confirmed). `DenunciasLista({ onEditar, tipo = "AGRESSIVO" })` ajusta o título e busca `/api/ccz/denuncias?tipo=...`. A segregação é dupla — filtro do fetch e `where` do servidor — então Agressivos só mostra `AGRESSIVO` e Doentes só `DOENTE` (confirmed). A barra "Lista / Novo" é genérica (`irPara(activeTab, ...)`), então as novas abas `DENUNCIA_AGRESSIVO`/`DENUNCIA_DOENTE` herdam a navegação sem código dedicado (confirmed).

### Sidebar: "Denúncias" como sub-dropdown aninhado

O item "Denúncias" ganha `isNestedDropdown: true` e `nestedItems` com "Animais agressivos" e "Animais doentes", espelhando a estrutura de "Zoonoses → Esporotricose" logo acima. A visibilidade é preservada: o item pai mantém `visivelSe: "CCZ"` e cada nested item repete `visivelSe: "CCZ"`, passando pelo recorte fail-closed de `subItemVisivel`. O `aria-expanded`/`aria-controls` são aplicados pelo render genérico de nested dropdown (`nestedListId`), sem mudança nesse mecanismo (confirmed).

Uma diferença de comportamento frente ao Esporotricose: os `path` dos novos itens trazem `&subTab=LISTA`. A lógica de destaque compara o `subTab` do destino com o atual quando o path o especifica — logo, ao navegar para "Novo" (`subTab=CADASTRAR`), o item aninhado perde o `activeLink`. O item Esporotricose, cujo path não traz `subTab`, destaca em qualquer sub-aba. Remover o `&subTab=LISTA` dos dois novos paths alinharia o destaque ao padrão existente (confirmed).
